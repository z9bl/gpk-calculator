# Инвентаризация пользовательских строк UI (views.js, labels.js, web/app.js)

Дата составления: 2026-09-14. Инвентаризация — без изменения кода, чисто документационная задача.

---

## 0. Методология

- Просмотрены полностью: `src/labels.js` (73 записи `INPUT_LABELS`), `web/app.js` (63 записи `INPUT_HINTS`, 2 записи `INPUT_HINTS_EXPIRED`, обе радио-группы через `renderRadioGroup` — `renderSudebnyPrikazFields`, `renderArbitrationAwardSetasideFields`, и статусные ветки `missed`/`expired`/`not_applicable`/`computed` в `renderTermCard`/`renderInfoTermCard`), `src/views.js` (проверен на предмет этих же четырёх категорий отдельно, см. §5 — самостоятельных строк не содержит).

- Текст каждой строки извлечён программным парсером прямо из исходников (не переписан вручную) и сверен построчно со значением, полученным вычислением объектного литерала в Node — расхождений не найдено (73/73 `INPUT_LABELS`, 63/63 `INPUT_HINTS`, 2/2 `INPUT_HINTS_EXPIRED`).

- Столбец «сверка нормы» сопоставлен с `docs/reports/norm-citations-inventory.json` (в задаче этот файл упомянут как `docs/norm-citations-inventory.json` — фактический путь в репозитории на момент инвентаризации: `docs/reports/norm-citations-inventory.json` и `.md`; ниже используется фактический путь). Сопоставление — по паре `file` + `line` (иногда `line_end`) с точностью до строки; для строк, распределённых по нескольким физическим строкам (конкатенация `+`), сверялись все строки диапазона.

- **Важно:** сама схема реестра (`id`, `file`, `line`, `line_end`, `node_or_context`, `source_type`, `justifies`, `duplicate_group_id`) не содержит поля со статусом сверки («сверено дословно» / «сверено по цитирующей публикации» / не помечено) для каждой записи — такой градации по `NC-id` в JSON/MD файле нет. Статус сверки в проекте фиксируется текстом в `SPEC.md` (§9, §11) на уровне статьи/нормы в целом, а не на уровне каждой записи реестра. Поэтому в столбце «сверка нормы» ниже указывается: найден ли по `file+line` соответствующий `NC-id` (и точная цитата в реестре), но не общий статус «дословно/по публикации» — присвоить его конкретной строке UI без обращения к SPEC.md и к первоисточнику нормы было бы домыслом. Это отдельно зафиксированное ограничение, а не пропуск в работе.

- Тег «форма» и «регистр» — фиксация текущего состояния текста, не оценка правильности (задача прямо просит не оценивать стиль и юридическую точность).

## 4. Статусные формулировки computed / missed / expired (`web/app.js`)

В отличие от групп 1–3, эти формулировки не привязаны к конкретному узлу-полю: одна и та же строка/шаблон используется для любого узла в соответствующем состоянии. Вариативность — не «по узлам», а по типу карточки: обычная карточка срока (`renderTermCard`) даёт один текст, информационная карточка срока суда (`renderInfoTermCard`, `informational: true`) — другой, более короткий. `src/views.js` только присваивает значения `status` (`'computed'`, `'missed'`(*), `'not_applicable'`, `'resolved'`/`'pending'` для событий) как коды — самого текста формулировок не содержит (см. §5). (*) `'missed'`/`'expired'` присваиваются в `core/view/cards.js` (`markExpired`), не в `src/views.js` — см. §5.

## 5. `src/views.js` — результат отдельной проверки

`src/views.js` явно назван в задаче как один из трёх файлов для инвентаризации, поэтому проверен по всем четырём
категориям отдельно, а не по умолчанию («раз там ничего не нашли в процессе — значит, нет»):

- **Подписи полей.** `src/views.js` не определяет собственных подписей — импортирует общий словарь `INPUT_LABELS`
  из `src/labels.js` (`import { INPUT_LABELS } from './labels.js'`, `src/views.js:65`) и использует его только как
  параметр функции `missingInputs()` (`src/views.js:106–108`, тонкая обёртка над `core/view/cards.js`). Собственного
  текста подписей нет — см. §1, где все записи уже атрибутированы `src/labels.js`.
- **Подсказки (hints).** Отсутствуют: `INPUT_HINTS`/`INPUT_HINTS_EXPIRED` определены и используются только в
  `web/app.js` (см. §2); `src/views.js` их не импортирует и не порождает.
- **Радио-группы.** `renderRadioGroup` и обе функции, которые её вызывают (`renderSudebnyPrikazFields`,
  `renderArbitrationAwardSetasideFields`), определены в `web/app.js`, а не в `src/views.js` — это функции слоя
  представления (DOM), тогда как `src/views.js` собирает только данные карточек (`buildView`), без вёрстки
  (см. собственный комментарий файла, `src/views.js:1–5`: «Никакой вёрстки — только данные»).
- **Статусные формулировки `computed`/`missed`/`expired`.** `src/views.js` присваивает **значения** статуса
  (`status: 'computed'` — например `src/views.js:181, 236, 354, 445, 528`; `status: entry.resolved ? 'resolved' :
  'pending'` — например `src/views.js:162, 322, 406, 495, 553`; `status: 'not_applicable'` — например
  `src/views.js:380, 468, 654`), но не текст, который увидит пользователь при `missed`/`expired` — эти два статуса
  вообще не устанавливаются в `src/views.js` (значения `'missed'`/`'expired'` присваиваются в
  `core/view/cards.js`, функция `markExpired`, которую `src/views.js` лишь оборачивает своими ГПК-картами
  `ACTION_FACT_INPUT`/`MISSED_FROM_FILING`, см. `src/views.js:1025–1036`). Сам пользовательский текст для этих
  статусов — только в `web/app.js` (см. §4). Единственное релевантное `src/views.js` — комментарии, поясняющие
  разницу между `'missed'` и `'expired'` для будущих читателей кода (`src/views.js:976–1004`), но это код-комментарии,
  не пользовательский UI-текст, поэтому в таблицы §1–4 не включены.

Итог: `src/views.js` не содержит собственных строк ни в одной из четырёх категорий — все четыре типа UI-текста,
которые он в конечном счёте показывает пользователю, либо приходят из `src/labels.js`/`web/app.js` как есть,
либо (для `not_applicable`/`resolved`/`pending`-сообщений — `card.message`, `entry.message`, `card.note`) как
данные из `src/chain.js`, который вне списка файлов этой задачи.

## 6. Итоговые наблюдения (фиксация состояния — без рекомендаций по стилю)

Эти наблюдения — только то, что фактически видно в таблицах §1–4; они не говорят, какой вариант «правильный».

1. **Форма.** Вопросительных формулировок (с «?») в проверенных категориях нет вообще — ни один заголовок,
   подсказка, вариант радио-группы или статусная строка не оформлена как вопрос. Подписи полей — почти все
   именные группы («Дата …»), кроме 4 исключений: `default_judgment_subject` («Кто обжалует …» — вопрос по
   смыслу, оформленный без «?»), `mirovoy_attendance` и `periodic_payment_indefinite` (глагольные утверждения),
   `review_discovered_during_cassation` (краткое причастие). Подсказки — все полные предложения-утверждения,
   кроме 8 подсказок для полей `*_restoration_circumstance_date` («Заполните, только если …») — единственная
   группа в побудительном наклонении во всём массиве. Подписи радио-опций различаются между собой: у
   `sudebny_prikaz_mode` — безличная констатация («Известна …»), у `arbitration_award_setaside_mode` — высказывание
   от первого лица («Я …», см. §3).
2. **Регистр.** Среди 73 подписей полей норму в тексте цитируют только 4 (`review_ground`,
   `child_return_reasoned_decision_date`, `child_return_interim_ruling_date`, `enforcement_interruptions`) — все
   остальные нейтрально описывают, какую дату ввести, без ссылки на статью. Среди 63 подсказок — обратная картина:
   54 из 63 содержат явную ссылку на статью/часть/пункт (см. §2), и лишь 9 нейтральны
   (`appeal_filed_date`, `appeal_ruling_date`, `appeal_ruling_reasoned_date`, `protocol_remarks_filed_date`,
   `default_judgment_refusal_date`, `default_judgment_cancellation_date`, `default_judgment_appeal_ruling_date`,
   `mirovoy_appeal_ruling_reasoned_date`, `foreign_state_default_judgment_appeal_filed_date`). Обе подсказки
   `INPUT_HINTS_EXPIRED` и обе подписи радио-опций норму не цитируют вовсе (в самом их литерале — у соседних
   узлов, к которым они относятся, норма процитирована в комментарии кода, не в пользовательском тексте, см. §3).
3. **Сверка нормы.** Для всех строк, где в тексте есть цитата статьи/главы/пункта, соответствующая запись в
   `docs/reports/norm-citations-inventory.json` **нашлась** — по паре `file`+`line` совпадений не пропущено, случаев
   «не найдено в реестре норм» в трёх проверенных файлах нет. Однако использовать это как «все цитаты сверены»
   нельзя: сама схема реестра не несёт градации «сверено дословно» / «сверено по цитирующей публикации» / не
   помечено на уровне записи — эта информация в проекте существует только как текст в `SPEC.md` §9/§11 на уровне
   конкретной статьи в целом (см. §0). Присвоение такого статуса каждой конкретной строке UI-текста было бы
   домыслом за пределами того, что зафиксировано в реестре, и не входило в эту инвентаризацию.
4. **Статусные формулировки.** У `computed` вообще нет отдельного текста — это неявное состояние по умолчанию.
   `missed` не имеет варианта для информационных карточек (`informational: true`) — в коде для таких карточек эта
   ветка не предусмотрена. `expired`, наоборот, есть в обоих типах карточек, но с разной степенью детализации:
   два предложения с пояснением «пропуск не подтверждён» у обычной карточки против одного короткого предложения
   у информационной (см. §4) — это и есть та «вариация по узлам» (точнее, по типу карточки), которую стоит иметь
   в виду при следующей точечной правке одной из двух веток в отрыве от другой.
