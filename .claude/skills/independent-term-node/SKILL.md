# Самостоятельный узел-срок: добавление, перенос, слияние

Этот файл — не теория, а зафиксированный фактический паттерн. Он выведен из
кода и из трёх применений: PR #82 (глава 45 — два узла одной главы), PR #97
(ситуация «Исполнительное производство» — новый узел с dropdown) и PR, который
свернул в него ситуацию «Периодические платежи».

**Важно.** Задача, поставившая PR #97, ссылалась на этот файл, когда его ещё не
существовало. Если промпт снова сошлётся на скилл, которого нет, — не блокируйся:
выведи паттерн из ближайших аналогов в коде и скажи об этом в отчёте.

## Что считается самостоятельным узлом

Узел, который считается **по своему input**, а не от `reasoned_decision_date`
через `computeChain`. Признаки: живёт в `computeIndependentTerms`, у него своя
ситуация в `SITUATIONS` (либо он в пуле `separate`), ни одна дата цепочки
обжалования не является его входом.

Образцы в коде, от близкого к далёкому:
- `enforcement_document_presentation` — **один узел на несколько вариантов**
  нормы, вариант выбирается dropdown'ом; есть ветка `not_applicable`;
- `review_new_circumstances_filing` — то же с семью основаниями
  (`REVIEW_GROUNDS` / `reviewTermFor`);
- `court_order_presentation` + `court_order_objection` — два независимых узла
  одной ситуации;
- `supervision`, `private_complaint` — простейший случай: один узел, один input.

## Карта мест (её и надо пройти целиком)

Ни один шаг не «необязательный»: пропуск любого из первых шести даёт либо
падающий тест, либо молча невидимый на экране узел.

| # | Файл | Что делать |
|---|---|---|
| 1 | `src/chain.js` | константа узла (`id`, `title`, `duration`, `anchor`, `weekend_shift`, `ics`, `logic`, `midnight_rule`, `restoration_norm`, `norm_versions`) и функция расчёта; ключ узла в объекте, который возвращает `computeIndependentTerms`, **и** его `@returns` в JSDoc |
| 2 | `src/situations.js` | ситуация: `id`, `label`, `fields`, `nodes`. `primary_field` **не занимать** — он зарезервирован за общей ветвью |
| 3 | `src/labels.js` | `INPUT_LABELS` для каждого нового поля — подпись в форме вопроса («Когда …?») |
| 4 | `src/views.js` | карточка: `if (terms.<id>) cards.push(<renderer>(terms.<id>))` в `independentCards`; при необходимости реэкспорт констант для UI |
| 5 | `web/app.js` | `INPUT_HINTS` для новых полей; вводный текст ситуации; спец-рендерер полей, если их набор зависит от выбора |
| 6 | `test/situations.test.js` | `ALL_BRANCHES_INPUTS` — данные, поднимающие узел; список id ситуаций и его счётчик в названии теста |
| 7 | `test/ics.test.js` | свой `ALL_BRANCHES_INPUTS` (отдельный от предыдущего!) — иначе упадёт проверка «каждый узел с `ics: true` попадает в файл» |
| 8 | `test/integration/boundary-sweep.test.js` | `LAYER2_INPUT_FIELD` — только если узел берёт якорь из одного поля без промежуточного resolve |
| 9 | `src/ics.js` | `icsTermsFromChain` — ручной список; трогать, только если правишь узел, который там уже перечислен |
| 10 | `SPEC.md` | описание узла в своём разделе; §«Вне модели», если чего-то узел намеренно не делает |
| 11 | `docs/reports/boundary-sweep-*.md` | **перегенерируется тестом** — просто закоммитить изменившийся файл |

Чего в этой карте нет и трогать не надо:
- `src/term-registry.js` — `TERM_REGISTRY` собирается перебором **всех**
  экспортов `chain.js` (`import * as chainModule`), поэтому экспортированная
  константа с `id`/`duration`/`ics` попадает в реестр .ics сама. Обратная
  сторона: удаление экспорта молча убирает узел из реестра;
- `reminderOffsets` — таблица по `duration`, новый узел известной длительности
  (3 года, 1/3/6 месяцев, рабочие дни) напоминания получает сам;
- `DEFAULT_SITUATION`, `situationById`, `allSituationNodes` — предметно-
  независимая механика в `core/view/situations.js`, хардкода id там нет;
- `exportableIds` в `web/app.js` — строится из видимых карточек, не из списка id.

## Инварианты, о которые спотыкаются

1. **Узел ровно в одной ситуации.** `checkSituationCoverage` проверяет по
   списку узлов, которые реально выдаёт `buildView`, а не по перечислению.
2. **Поле ввода ровно в одной ситуации** (`allSituationFields`, без дублей).
   Отсюда главное следствие для переиспользования: если новая ситуация якорится
   на поле, которое уже принадлежит другой, **в `fields` его перечислять
   нельзя** — рисуй его спец-рендерером по `anchor_field` выбранного варианта.
   Это безопасно: в каждый момент отрисовывается ровно одна ситуация, а
   `renderedFields` чистится каждым `render()`.
3. **В ситуациях нет узлов, которых модель не выдаёт** — обратная проверка;
   поэтому `ALL_BRANCHES_INPUTS` обязан поднимать новый узел.
4. **Заголовок узла уникален.** `icsTermsFromView` и проверки экспорта ищут
   карточку **по title**; два узла с одинаковым заголовком путают их (у копий
   `*_enforcement_presentation` внутри ветвей заголовки совпадают — это
   исторический случай, новые так делать не надо).
5. `ics: true` без `duration`, известного `reminderOffsets`, даёт срок в файле
   **без напоминаний** и молча.

## Один узел на несколько вариантов нормы

Если норма и/или якорь зависят от выбора пользователя — это **один узел**, а не
несколько. Образцы: `REVIEW_GROUNDS`/`reviewTermFor`,
`ENFORCEMENT_DOCUMENT_TYPES`/`enforcementDocumentTermFor`.

Устройство: таблица вариантов (`id`, `label`, `anchor_field`, `logic`, `norm` и
любые предметные флаги) + функция, собирающая `term` на лету + `*ById()` для UI.
Общее (длительность, `offset_start`, `weekend_shift`) задаётся в функции,
различия живут в таблице. **Предметное свойство — в таблицу, механику — в
функцию:** применимость ст. 22 (`interruptible`), наличие чекбокса-альтернативы
(`indefinite_field`) — это свойства варианта, а не механизма.

Карточка при этом одна, и выбор её переписывает. Узел без выбранного варианта
возвращает `null` (якорь неизвестен), а не «недостаточно данных»: у вариантов
разные якорные поля, и спрашивать «какую дату» до выбора варианта нечего.

## Механику не копировать

Перерыв и вычет ст. 22 ФЗ № 229-ФЗ подключаются одной строкой и **полностью
переиспользуются**, включая UI:

- расчёт — `computeInterruptibleTerm(term, anchorDate, inputs.enforcement_interruptions)`
  (обёртка в `chain.js` над `core/engine/interruption.js` + `deduction.js`);
- карточка — `attachInterruptions(card, term)` + `attachDeductions(card, term)`;
- форма ввода — **ничего не делать**: `renderInterruptions` вешается на карточку
  по признаку `card.interruptible`, а истории — по наличию `card.interruptions` /
  `card.deductions`. Блок «Добавить событие» появляется сам.

Список событий один на все узлы (`enforcement_interruptions`) и привязан не к
ситуации, а к карточке. Поэтому «доступен тот же блок событий» не требует правок
в `web/app.js` вообще.

## Перенос и слияние узлов (поглощение ситуации-обёртки)

Если существующая ситуация — тонкая обёртка над тем же расчётом, её сворачивают
в вариант другого узла. Порядок:

1. **Сначала аудит, до удаления.** Выгрузить все вхождения id ситуации и id
   узла: `grep -rn "<id ситуации>'\|<id узла>" src web test scripts docs SPEC.md index.html`.
   Пройти карту мест выше в обратную сторону. Отдельно проверить `src/ics.js`
   (ручной список) и `test/integration/boundary-sweep.test.js`
   (`LAYER2_INPUT_FIELD`) — они не находятся «по смыслу», только грепом.
2. **Перенести логику целиком, а не похоже.** Все предметные особенности узла
   переезжают в таблицу вариантов: якорь, текст оговорки, взаимоисключающие
   поля, ветки `not_applicable`, применимость модификаторов. Два похожих
   блока кода вместо одного — признак, что перенос не доделан.
3. **Поведение сохранять, а не выравнивать по соседям.** Если поглощаемый узел
   чего-то намеренно не делал (у периодических платежей — не применялась
   ст. 22, §«Вне модели» SPEC.md), это его логика, и она переезжает вместе с
   ним. Выравнивание — отдельная содержательная задача, не часть переноса;
   вынеси её в отчёт, а не решай по ходу.
4. **Поля поглощённой ситуации перечислить в `fields` новой** — после удаления
   старой они больше никому не принадлежат, и инвариант 2 их требует.
5. **Тест, сравнивавший два входа, не удалять молча.** После слияния второй
   стороны сравнения нет. Либо переформулируй его в проверку того, что
   перенесённая логика работает внутри нового узла, либо объясни в отчёте,
   почему прежняя форма потеряла смысл. В самом файле теста напиши, что
   изменилось и почему, — иначе следующий читатель решит, что проверку
   потеряли.
6. **Добавить охранный тест** на то, что старый id больше не выдаётся
   `buildView` ни под каким видом: иначе узел-дубликат может вернуться незаметно.
7. `docs/reports/norm-citations-inventory.md` — исторический снимок с номерами
   строк, **никем не генерируется**. После переноса он устаревает; это ожидаемо,
   переписывать его в рамках задачи не нужно — упомяни в отчёте.

## Проверка

```
npm test                                   # инварианты разбиения, .ics, карточки
node scripts/smoke.mjs                     # браузер: без ошибок в консоли
```

`npm test` + smoke не проверяют новую ситуацию содержательно: smoke ходит только
по общей ветви. Для узла с dropdown или взаимоисключающими полями прогони
одноразовый playwright-скрипт (его кладут в `scripts/`, чтобы совпал `ROOT`,
и удаляют после прогона — в репозиторий он не идёт): выбор ситуации, каждый
вариант dropdown'а → своё якорное поле, норма и дедлайн на карточке, наличие или
отсутствие блока «Добавить событие», ровно одна карточка в ситуации.

Осторожно с ассертами по тексту: CSS в `index.html` делает `text-transform:
uppercase` у заголовков блоков, и `innerText` возвращает уже преобразованный
текст («ПЕРЕРЫВЫ СРОКА»).

## Что выносить в отчёт, а не решать самому

- точное название ситуации/узла и id новых полей — предлагать, помечая как
  предложение (соглашение об именовании: `<субъект>_entry_into_force_date`,
  `*_ruling_date`, `*_received_date`);
- нужна ли валидация на совпадение или пересечение введённой даты с другими
  датами модели;
- выравнивание поведения, которое расходится между узлами, — см. шаг 3 выше;
- любую правку в `core/` или в соседнем домене (`apk/`): по CLAUDE.md это повод
  остановиться и спросить, а не делать по своей инициативе.
